## Goal
The chat model gets one tool, `search_documents(query)`. When a question may be answered by the user's uploaded documents, the model calls the tool. The backend embeds the query, calls the `match_chunks` RPC under the user's JWT (so RLS applies), and returns the top chunks with filename/chunk citations. The model then answers from them and cites the sources. If nothing clears the relevance threshold, the model says the documents don't cover the question. The existing "Searching documents…" indicator keeps working off the same SSE `tool` events, and each turn shows up in LangSmith as `chat_turn` → LLM call → `search_documents` (tool) → embedding + `match_chunks` (retriever) → LLM call.

## Decisions

**D1. Persist only the final assistant text; never persist tool-call or tool-result messages.**
History stays as `user`/`assistant` text, and the `role` check constraint is unchanged. Reasons:
1. Chat Completions requires every assistant `tool_calls` entry to be followed by matching `tool` messages. A turn stopped mid-tool-call would leave an orphan pair that makes every later turn in the thread fail with a 400. Text-only history rules out that whole class of bug.
2. Resending 5 chunks per past turn grows the token cost with thread length. It also keeps feeding the model chunks from documents the user has since deleted (2.2 cascades chunk deletes).
3. The model can search again cheaply. Inline citations in the saved text (filenames) give follow-ups enough to re-query precisely.

Trade-off accepted: a follow-up like "expand on point 2" triggers a fresh search instead of reusing the old chunks.
Schema change (only with Task 9): a nullable `messages.sources jsonb` holding citation metadata for display (`document_id, filename, chunk_index, similarity`). It is **never** sent to the model. Module 8 (nested tool display) can extend this later to a `tool_calls jsonb` display column without changing the history contract.

**D2. Defaults: `RETRIEVAL_TOP_K=5`, `RETRIEVAL_MIN_SIMILARITY=0.30`.**
- `text-embedding-3-small` cosine similarities are compressed. Unrelated text usually lands around 0.05–0.20, topically related passages around 0.30–0.60, and near-paraphrases 0.70 and up. 0.30 drops clear noise but keeps loosely phrased questions.
- 5 chunks of 2.2's chunk size is a few thousand tokens per search: enough for multi-passage answers, cheap, and well inside context. It leaves room for Module 6 reranking (fetch more, rerank down).
- Both are env-configurable. Task 2's calibration script prints real similarity scores so you can tune them on your corpus. The SQL function also clamps `match_count` to 1..50.

**D3. Default model must support tools on OpenRouter.**
- Default `LLM_MODEL=openai/gpt-4.1-mini`: reliable streamed tool calls and parallel calls, cheap.
- When `LLM_BASE_URL` contains `openrouter.ai`, send `extra_body={"provider": {"require_parameters": True}}` so OpenRouter routes only to providers that honour `tools`/`tool_choice`, instead of silently dropping them.
- Validate a model with `curl -s https://openrouter.ai/api/v1/models | jq '.data[] | select(.id=="<model>") | .supported_parameters'`. It must include `"tools"` and `"tool_choice"`. Document this in `.env.example`.

**D4. Bounded loop.** `AGENT_MAX_TOOL_ROUNDS=3`: at most 3 rounds of tool execution, then one last model call with `tool_choice="none"`. `tools` stays in that call because some providers reject `tool` messages when no tools are declared. At most 4 model calls per turn.

**D5. No `strict` JSON schema mode and no `parallel_tool_calls` param.** Not every provider supports them. Pydantic validates the arguments on our side instead. Validation failures go back to the model as tool results so it can retry.

### 1. Migration `supabase/migrations/0004_match_chunks.sql`
```sql
-- Module 2.3: vector search over the caller's own chunks. SECURITY INVOKER, so RLS on
-- chunks/documents applies; the explicit auth.uid() filter is defence in depth.
create or replace function public.match_chunks(
  query_embedding vector(1536),
  match_count int default 5,
  match_threshold float default 0.30
)
returns table (
  id uuid, document_id uuid, filename text, chunk_index int, content text, similarity float
)
language sql stable
security invoker
set search_path = public, extensions
as $$
  select c.id, c.document_id, d.filename, c.chunk_index, c.content,
         1 - (c.embedding <=> query_embedding) as similarity
  from public.chunks c
  join public.documents d on d.id = c.document_id
  where c.user_id = (select auth.uid())
    and d.status = 'completed'
    and 1 - (c.embedding <=> query_embedding) >= match_threshold
  order by c.embedding <=> query_embedding
  limit least(greatest(match_count, 1), 50);
$$;

revoke execute on function public.match_chunks(vector, int, float) from public, anon;
grant execute on function public.match_chunks(vector, int, float) to authenticated;
```
- Notes:
  - If 2.2 installed `vector` in a schema other than `extensions`, adjust `search_path`.
  - If `select extversion from pg_extension where extname='vector'` is ≥ 0.8.0, add `set hnsw.iterative_scan = relaxed_order` to the function's `SET` clauses. Otherwise the HNSW scan with the `user_id` filter can return fewer than k rows once many users share the table. This doesn't matter at dev scale, where the planner seq-scans anyway.
- Apply it in the SQL editor (or `supabase db push`).
- *Validate (SQL editor):*
  - `select prosecdef from pg_proc where proname='match_chunks'` → `false` (invoker).
  - `select has_function_privilege('anon','public.match_chunks(vector,int,float)','execute')` → `false`.
  - Impersonation check (one transaction):
    ```sql
    begin;
    set local role authenticated;
    set local request.jwt.claims = '{"sub":"<user A uuid>","role":"authenticated"}';
    select distinct filename from match_chunks((select embedding from chunks limit 1), 50, -1);
    rollback;
    ```
    It lists only A's filenames. Repeat with B's uuid: only B's. Get the uuids from `auth.users`.

### 4. Tool definition and executor `backend/app/services/tools.py`

  ```python
  class SearchDocumentsArgs(BaseModel):
      query: str = Field(min_length=2, max_length=500, description=
          "A self-contained search query. Rewrite follow-ups into standalone form, "
          "e.g. 'refund policy for annual plans' rather than 'what about that?'")
  ```

- `class ToolResult(BaseModel): content: str; sources: list[Source]`, where `Source = {document_id, filename, chunk_index, similarity}`.
- `TOOL_SCHEMAS = [{"type": "function", "function": {"name": "search_documents", "description": "Semantic search over the documents the user has uploaded. Returns the most relevant passages with filename and chunk number. Use for any question that might be answered by the user's documents.", "parameters": SearchDocumentsArgs.model_json_schema()}}]`. Pop the Pydantic `title` keys for tidiness.
- `@traceable(run_type="tool", name="search_documents") async def search_documents(args: SearchDocumentsArgs, ctx: ToolContext) -> ToolResult`:
  - Calls `search_chunks` with settings `top_k`/`min_similarity`.
  - Formats results most relevant first:
    ```
    Found 3 passages from the user's documents (most relevant first).
    Cite as (filename, chunk N).

    [1] handbook.md, chunk 12 (similarity 0.62)
    <content>

    [2] …
    ```
  - Empty result: `"No passages in the user's documents matched this query (minimum similarity 0.30). Do not invent an answer from the documents; tell the user their documents don't appear to cover this."`
- `async def execute_tool(name: str, raw_args: str, ctx) -> ToolResult` is the dispatcher and never raises to the loop:
  - Unknown name → `ToolResult(content="Unknown tool …", sources=[])`.
  - `json.JSONDecodeError` or `pydantic.ValidationError` → `content="Invalid arguments: <short error>. Call again with {\"query\": \"…\"}"`.
  - Any other exception (embedding API down) → `content="Search failed: <message>"`. The loop emits `status: "error"`.

### 5. Streamed tool-call accumulator and agent loop in `backend/app/services/llm.py`
- **`ToolCallAccumulator`** is pure, with no I/O, so it can be unit-tested. Put it in `backend/app/services/tool_calls.py`.
  - `add(deltas: list[ChoiceDeltaToolCall] | None)`: keyed by `delta.index`. If `index` is missing, use the key of the last call opened, or 0. Keep the first non-empty `id` and `function.name`, and concatenate `function.arguments` fragments.
  - Handles both providers that stream arguments piecemeal and providers that send a complete call in one chunk.
  - `calls() -> list[ToolCall(id, name, arguments)]` in index order. Synthesize `id=f"call_{index}"` when the provider sends none.
  - `__bool__` = any calls.
- **Loop** (see Reconciliation: each round goes through 2.1's `stream_completion`, which now carries `tool_calls` in its `completion` event):
  ```
  text_parts, sources = [], []
  for round in range(max_rounds + 1):
      final = round == max_rounds
      async with aclosing(stream_completion(messages, tools=TOOL_SCHEMAS if ctx else None,
                          tool_choice="none" if final else "auto")) as rounds:
          round_text = []
          async for ev in rounds:
              if ev["type"] == "delta":
                  if text_parts and not round_text: yield delta "\n\n"; text_parts.append("\n\n")
                  round_text.append(ev["delta"]); text_parts.append(ev["delta"]); yield ev
              elif ev["type"] == "completion": completion = ev
      if completion["finish_reason"] == "error": yield error; return     # from 2.1
      calls = completion["tool_calls"]
      if not calls or final: break          # decide on calls, not finish_reason (providers disagree)
      messages.append({"role":"assistant","content": "".join(round_text) or None,
                       "tool_calls":[{"id","type":"function","function":{"name","arguments"}}…]})
      for call in calls:                     # sequential; parallel calls are rare and cheap
          yield {"type":"tool","name":call.name,"status":"searching","query":<parsed query or None>}
          result = await execute_tool(call.name, call.arguments, ctx)
          messages.append({"role":"tool","tool_call_id":call.id,"content":result.content})
          sources += result.sources
          yield {"type":"tool","name":call.name,"status":"completed" | "error","sources":[…]}
  yield {"type":"done","text":"".join(text_parts),"sources":dedupe(sources)}
  ```
  - If the final round still returns tool calls (a model ignoring `tool_choice`) and no text, yield `done` with text "I couldn't complete the search in time. Please rephrase the question."
  - If a provider rejects `content: None` on the assistant tool-call message, use `""`.
  - `provider_extra = {"extra_body": {"provider": {"require_parameters": True}}}` only when the base URL contains `openrouter.ai` (D3). Apply it inside `stream_completion`.
- **Cancellation**: client disconnect → `CancelledError`/`GeneratorExit` at the current await.
  - While streaming: `async with stream` closes the HTTP stream, as in 1.4.
  - During `embed_query`: async httpx cancels immediately.
  - During the RPC thread: `anyio.to_thread.run_sync` waits for the sub-second query to finish, then raises the cancellation. Acceptable. Don't use `abandon_on_cancel`, so connections aren't leaked.
  - LangSmith then marks both the tool run and `chat_turn` as cancelled or errored.
  - The router's existing `finally` saves partial text if there is any. A stop during the first search (no text yet) saves nothing. The next turn then has two consecutive `user` messages, which Chat Completions accepts and D1 makes safe.
- **Tracing**: `search_documents` (`@traceable run_type="tool"`) is awaited inside the `chat_turn` generator, so it nests through contextvars. The embedding call (wrap_openai) and `match_chunks` (retriever) nest under it. anyio 4.x `to_thread.run_sync` copies contextvars. **Fallback** if the RPC run appears top-level: capture `parent = langsmith.get_current_run_tree()` before the thread hop and pass `langsmith_extra={"parent": parent}`.
- *Validate:* `python -c "import app.services.llm"`. The Task 6 tests pass.

## Single-pass feasibility
Yes, with 2.1 and 2.2 validated first. Iteration is most likely in three places, each with a fallback above:
- **Provider tool-call streaming quirks:** the accumulator handles missing index and id, and the loop decides on the collected calls instead of `finish_reason`.
- **The RPC vector param encoding:** fall back to `str(embedding)`.
- **LangSmith nesting across the thread hop:** pass an explicit `parent`.

Calibrating the threshold is a measurement, not a redesign. Task 9 is independent and can be cut.

## Out of scope (left room for)
- Metadata filters as extra tool args (Module 4): add fields to `SearchDocumentsArgs` and params to `search_chunks`.
- Hybrid search plus reranking (Module 6): replace the RPC inside `retrieval.search_chunks` only.
- More tools such as text-to-SQL and web search (Module 7): add to `TOOL_SCHEMAS` and the `execute_tool` dispatch. The loop is already multi-tool.
- Persisted or nested tool-call display (Module 8): a display-only `jsonb` column, per D1.
