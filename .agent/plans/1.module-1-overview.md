# Module 1 Overview: App Shell + Observability

🔴 **Complex** (index plan): split into sub-plans 1.1 → 1.2 → 1.3, each built and validated separately.

## Goal
Supabase auth, a threaded chat UI, and chat powered by OpenAI's **Responses API** (managed conversation state plus built-in `file_search`), streamed over SSE, with LangSmith tracing from day one. This is "managed RAG": OpenAI holds the memory and the retrieval. Module 2 contrasts it with BYO retrieval.

## Decisions
- **Supabase:** hosted project. The user supplies the URL and keys in `.env`. The schema lives in SQL migration files, applied via the SQL editor (or `supabase db push`).
- **file_search docs:** the user creates an OpenAI vector store in the dashboard, uploads a few files and sets `OPENAI_VECTOR_STORE_ID`. Module 1 has no upload UI.
- **Thread state:** OpenAI **Conversations API**. A Supabase `threads` row stores `openai_conversation_id`, and a `messages` table mirrors messages for fast UI rendering.

## Env vars
- backend: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `OPENAI_API_KEY`, `OPENAI_MODEL` (default `gpt-4.1-mini`), `OPENAI_VECTOR_STORE_ID`, `FRONTEND_ORIGIN`, `LANGSMITH_TRACING`, `LANGSMITH_API_KEY`, `LANGSMITH_PROJECT`
- frontend: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_API_URL`

## User prerequisites (manual)
- A Supabase project with email auth enabled (disable email confirmation for dev).
- An OpenAI key and a vector store with sample docs.
- A LangSmith key.

## End-to-end acceptance
1. Sign up or log in.
2. Create a thread.
3. Ask a question that the vector-store docs answer. The answer streams token by token.
4. Reload the page. The thread and its history persist.
5. A second user cannot see the first user's threads.
6. The run appears in LangSmith with the file_search step.

## Run
- Backend: `cd backend && venv/bin/uvicorn app.main:app --reload`
- Frontend: `cd frontend && npm run dev`
