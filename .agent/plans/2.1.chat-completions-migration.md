# 2.1 Replace the Responses API with Chat Completions + self-managed history

⚠️ **Medium**: a small surface (5 backend files changed, 1 new backend module, 1 migration, docs, no frontend code changes). The logic risk is low, but there are two human gates (an `LLM_API_KEY` in `backend/.env` and applying a migration to the hosted Supabase), plus some provider-specific streaming quirks (usage-only chunks, `finish_reason: "error"`). Single-pass feasible once the key is in place.

Parent: Module 2 (BYO Retrieval + Memory), see `2.module-2-overview.md`. Sibling sub-plans: 2.2 ingestion (runs independently), 2.3 `search_documents` tool (builds on this plan's `services/llm.py`).

SDK notes (installed `openai` 3.40.0, `langsmith` 0.14.13 in `backend/venv`):
- **Mid-stream errors raise.** `AsyncStream.__stream__` raises `openai.APIError` when an SSE chunk carries an `error` key, which is how OpenRouter reports mid-stream failures. So `except openai.OpenAIError` catches them.
- **Closing the stream works the same way.** `AsyncStream` supports `async with`, so the 1.4 cancellation approach still applies.

## Goal
- Chat runs on the standard **Chat Completions API** through the raw `openai` SDK, pointed at any OpenAI-compatible base URL. The default is OpenRouter.
- The model is **stateless**. Each turn the backend loads the thread's history from `public.messages`, trims it to a window, adds an optional system prompt and sends the whole list.
- **Option A: Replace.** Every bit of Responses API code goes: `conversations.create/delete`, `responses.create`, `file_search`, `OPENAI_VECTOR_STORE_ID`, `OPENAI_MODEL`, and the `threads.openai_conversation_id` column (new migration `0002`). Creating and deleting threads no longer calls OpenAI.
- **Unchanged**:
  - the SSE event shape (`delta` / `tool` / `done` / `error`)
  - the Stop button behaviour (a disconnect cancels the upstream stream and the partial reply is saved)
  - LangSmith (`wrap_openai` plus `@traceable chat_turn`)
  - RLS
  - the frontend
- **Side effect (fixes a Module 1 follow-up):** a stopped partial reply is already saved to `messages` (1.4). History now comes from `messages`, so the partial answer is part of the next turn's context. The "thread delete waits on `conversations.delete`" follow-up also goes away.
- **Out of scope:** retrieval and tool calling (2.3), embeddings and ingestion (2.2). No LangChain or LangGraph.

## Design decisions

### Env vars
| Var | Default | Purpose |
|---|---|---|
| `LLM_BASE_URL` | `https://openrouter.ai/api/v1` | Any OpenAI-compatible endpoint (OpenRouter, Ollama `http://localhost:11434/v1`, LM Studio `http://localhost:1234/v1`) |
| `LLM_API_KEY` | `""` | Provider key. If empty, the chat turn returns a clear `error` event |
| `LLM_MODEL` | `openai/gpt-4.1-mini` | Provider model id. Pick a tool-calling-capable model because 2.3 needs one |
| `CHAT_SYSTEM_PROMPT` | `""` | Optional. If set, it is sent as the first `system` message |
| `CHAT_HISTORY_MAX_MESSAGES` | `20` | Upper bound on the number of stored messages sent per turn |
| `CHAT_HISTORY_MAX_CHARS` | `24000` | Character budget for the history window (about 6k tokens) |
| `CHAT_MAX_OUTPUT_TOKENS` | `4096` | Sent as `max_tokens`. Added during the build: without it OpenRouter reserves credit for the model's full output limit and returns 402 on low-credit keys |
| `OPENAI_API_KEY` | kept | Unused by chat after 2.1. Kept for embeddings in 2.2 |

`LLM_*` settings describe the provider connection. `CHAT_*` settings describe chat behaviour, which is independent of the provider.

### History window: last 20 messages, then a 24,000-character budget
- **Rule:** fetch the newest `CHAT_HISTORY_MAX_MESSAGES` rows (`order created_at desc limit N`, then reverse). Drop the oldest messages until the total `content` length is within `CHAT_HISTORY_MAX_CHARS`. Then drop any leading `assistant` messages so the window starts on a `user` turn. The **current user message is always kept**, even if it alone is over budget (`ChatRequest` allows up to 20,000 chars).
- **Why a message count plus a character budget, not real token counting:**
  - The model is configurable across providers, so no single tokenizer is correct. `tiktoken` would add a dependency and would still be wrong for Claude, Llama or Qwen models behind OpenRouter. At roughly 4 characters per token, the character budget is a predictable approximation that works with any provider.
  - 20 messages (10 turns) keeps short-term conversational memory, which is what the PRD asks for. The `limit` also keeps the DB read small for long threads.
  - About 6k tokens of history fits every mainstream hosted model with plenty of room. It also leaves room for 2.3, where retrieved chunks are added to the context within a turn. For small local models (8k context in LM Studio or Ollama), lower `CHAT_HISTORY_MAX_CHARS` in `.env`.
  - Summarizing old turns is a possible future improvement and is not done here.
- **Where trimming lives:** a pure function in a new `services/history.py`, so it can be unit-checked with `python -c` and 2.3 never touches it.
- **Known edge case (accepted, not fixed):** an errored turn, or one stopped before the first token, leaves a user message with no assistant reply. The next request then has two consecutive `user` messages. OpenAI, OpenRouter and its Anthropic routing all accept this. We send history as stored rather than merging messages.

### Insert first, then load
`send_message` already inserts the user message before streaming. History is loaded **after** that insert, so what the model sees is exactly what is stored, with the DB as the single source of truth. The RLS-scoped user client reads the history, so a user can never load another user's messages.

**2.3 hook point:** `stream_reply` is the agent loop. 2.3 replaces its single `stream_completion(messages)` call with a bounded loop:

```
for round in range(MAX_TOOL_ROUNDS):
    stream_completion(messages, tools=TOOLS)
    if completion.finish_reason == "tool_calls":
        append assistant tool_calls msg
        yield tool searching
        run search_documents (@traceable run_type="tool")
        append role="tool" msg
        yield tool completed
        continue
    break
```

For this, 2.3 also has to (a) collect `choice.delta.tool_calls` by `index` in `stream_completion` and (b) add `tool_calls` to the internal `completion` event. 2.1 leaves a `# 2.3:` comment at both spots. The frontend already handles `tool` events ("Searching documents…" indicator), so 2.3 needs no frontend change. The SSE contract and `routers/chat.py` stay untouched in 2.3.

### 2. `backend/app/services/history.py` (new): load + trim
- `trim_history(messages: list[dict], max_messages: int, max_chars: int) -> list[dict]`. This is pure:
  1. Keep the last `max_messages`.
  2. Drop the oldest while the summed `len(content)` is over `max_chars` and more than 1 message remains.
  3. Drop leading `assistant` messages while more than 1 remains.
  4. Return `[{"role", "content"}]` dicts only, with no ids or timestamps.
- `load_history(db: Client, thread_id: str) -> list[dict]`:
  - `db.table("messages").select("role,content").eq("thread_id", thread_id).order("created_at", desc=True).limit(settings.chat_history_max_messages).execute().data`
  - then reverse it and return `trim_history(...)`.
- *Validate:*
  ```
  cd backend && venv/bin/python -c "
  from app.services.history import trim_history as t
  m=lambda r,c:{'role':r,'content':c,'id':'x'}
  h=[m('user','a'*10),m('assistant','b'*10),m('user','c'*10),m('assistant','d'*10),m('user','e'*10)]
  assert t(h,20,1000)==[{'role':x['role'],'content':x['content']} for x in h]
  assert [x['content'][0] for x in t(h,4,1000)]==['c','d','e']      # count limit + no leading assistant
  assert [x['content'][0] for x in t(h,20,25)]==['e']                # char budget, starts on user
  assert t([m('user','z'*50000)],20,100)[0]['content']=='z'*50000    # current msg always kept
  print('ok')"
  ```

### 3. `backend/app/services/llm.py`: rewrite on Chat Completions
- **Delete:**
  - `get_client` (sync) and `get_async_client`
  - `create_conversation` and `delete_conversation`
  - the whole `responses.create` / `file_search` body
- **Add** `get_chat_client`, `build_messages`, `stream_completion` and `stream_reply(history)` as described in the design section. Keep `_final_event` and the `@traceable(name="chat_turn", run_type="chain", reduce_fn=_final_event)` decorator.
- **`stream_completion` details:**
  - The call is `await client.chat.completions.create(model=settings.llm_model, messages=messages, tools=tools or openai.omit, stream=True, stream_options={"include_usage": True})`. `include_usage` makes LangSmith record token counts.
  - Iterate inside `async with stream:` so a cancellation closes the provider HTTP stream (same as 1.4).
  - **Skip chunks with empty `choices`.** The final usage-only chunk from OpenAI and OpenRouter has `choices == []`, and indexing `[0]` would crash.
  - For `choice.delta.content`, add it to the parts and yield a `delta` event. Record `choice.finish_reason` when it is set.
  - After the loop, yield the internal `completion` event.
- **`stream_reply` details:**
  - Wrap the inner generator in `contextlib.aclosing(stream_completion(...))` so that closing the outer generator closes the inner one (and its `async with stream`) right away instead of at GC.
  - Do not forward the `completion` event. If `finish_reason == "error"` (an OpenRouter in-band upstream failure), yield `{"type": "error", "message": "The model provider returned an error"}` and return. Otherwise yield `{"type": "done", "text": content}`.
  - Catch `openai.OpenAIError` and the `RuntimeError` for a missing key, and turn them into `error` events. A mid-stream `{"error": ...}` SSE chunk already arrives as `openai.APIError`.
  - Do not catch `asyncio.CancelledError`, so the Stop button still cancels.
- Add the two `# 2.3:` comments (tool-call collection in `stream_completion`, and the loop point in `stream_reply`).
- *Validate:* `venv/bin/python -c "import app.services.llm as l; print(l.build_messages([{'role':'user','content':'hi'}]))"` prints the list (with a system message only if `CHAT_SYSTEM_PROMPT` is set). `grep -n "conversation\|responses\.\|file_search\|vector_store" backend/app/services/llm.py` prints nothing. ## Single-pass feasibility
**Yes, with two pauses for the user:** the `LLM_API_KEY` (task 0) and applying migration 0002 (task 7).
- **Work size:** about 6 backend files, no frontend code, and no new dependencies (`openai` 3.40 already supports `base_url` and `stream_options`).
- **Most likely iterations:**
  - (a) a provider-specific chunk shape (handled by the empty-`choices` guard and the `finish_reason == "error"` branch)
  - (b) a wrong OpenRouter model id (fix in `.env`)
  - (c) forgetting to run the code change before the migration (the order is enforced in task 7)

## Final regression checklist
- [ ] Auth: `curl localhost:8000/api/me` with no token returns 401 and a bad token returns 401. With the backend up, the browser sign-in → reload keeps the session → sign-out flow works. A deep link returns to its URL after login.
- [ ] RLS: anon REST `select` on `threads` and `messages` returns `[]`. User B gets **404** on user A's thread for GET messages, POST messages (no user row inserted), PATCH and DELETE.
- [ ] Thread CRUD: create, list, rename and delete via curl. Create and delete make no OpenAI calls and are fast.
- [ ] Streaming: curl SSE shows several `delta` events, then `done`. The browser renders progressively.
- [ ] Memory: a follow-up question uses earlier turns in curl, the browser and `smoke_chat --memory`.
