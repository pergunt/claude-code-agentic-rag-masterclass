# 2.2 Document ingestion: upload → storage → chunk → embed → pgvector, with Realtime status and an Ingestion UI

⚠️ **Medium**: many files across 4 layers (SQL + Storage + backend pipeline + React page with Realtime), but each piece is simple and has a clear validation. Single-pass feasible, with **two human steps**: add `SUPABASE_SERVICE_ROLE_KEY` to `backend/.env`, and apply the migration in the Supabase SQL editor. If the run has to stop partway, the natural checkpoint is after Task 6 (backend fully validated with curl). Tasks 7 to 8 (UI) can then run as a second pass.

Parent: Module 2, see `2.module-2-overview.md`. Depends on: Module 1 (auth, `db.py`, `api.ts`) and is built **after 2.1** (see the overview for why the order is sequential). 2.1 and 2.2 both touch `config.py`, `.env.example`, `requirements.txt` and `main.py`, but only by adding lines. 2.3 (retrieval) depends on the **contract** section below.

Findings from the current code that shape this plan:
- **`python-multipart` is missing.** It isn't installed in `backend/venv`, and FastAPI needs it for `UploadFile`. `start-services.sh` only installs requirements when it creates the venv, so new dependencies are never picked up on an existing setup.
- **`create_user_client` doesn't cover Storage.** It only calls `postgrest.auth(jwt)`. In supabase-py 2.33, `client.storage` uses `options.headers["Authorization"]`, which is the anon key. Storage calls would run as anon and fail the per-user policies.
- **Uploads would be sent as JSON.** `frontend/src/lib/api.ts` `request()` always sets `Content-Type: application/json`, which breaks a `FormData` upload.

## Goal
A signed-in user opens **Documents** from the chat sidebar and drops one or more `.txt`/`.md` files (or picks them). Each file is:
1. validated (type, size, UTF-8)
2. stored in a private Storage bucket at `{user_id}/{document_id}/{filename}`
3. recorded as a `documents` row with status `pending`

After the response is sent, the backend processes the file: `processing`, then download, chunk, embed (OpenAI `text-embedding-3-small`, 1536 dims), insert into `chunks`, then `completed` (or `failed` with an error). The list updates live through Supabase Realtime. Deleting a document removes its chunks (cascade) and its storage object.

Out of scope (later modules, don't build them): dedup/content hashing (M3), metadata extraction (M4), PDF/DOCX/HTML (M5), retrieval/`match_chunks` (2.3), connectors.

## Key decisions

### 1. Processing runs in FastAPI `BackgroundTasks`, not a separate worker
- **Why:** zero new services: no queue, no worker process, no change to `start-services.sh` or the CLAUDE.md services table. The work is I/O-bound (Storage download, a few OpenAI calls, PostgREST inserts). A sync task runs in Starlette's threadpool, so it doesn't block the event loop. A `.md` file finishes in about 1 to 3 s.
- **Known weakness:** tasks are in-process. A server restart, including `uvicorn --reload` when a file is saved mid-ingest, kills them and leaves rows stuck at `pending`/`processing`.
- **Fix:** a startup sweep in the FastAPI lifespan. On boot, every `pending`/`processing` document is marked `failed` with `error = "Processing was interrupted by a server restart. Delete and upload again."` This is correct because only one backend instance runs in dev (`restart-services.sh` guarantees that) and tasks never outlive the process.
- **Rejected alternative:** a DB-polling worker. It's more robust, but it means another process, another entry in the start/restart scripts, claim/lock logic, and polling. Revisit if Module 5 (docling PDFs) makes jobs long. The pipeline is one function, `process_document(document_id)`, so moving it into a worker later is a small change.

### 2. The background processor writes with the **service role**. Request handlers stay on the user's JWT under RLS
- **Problem with the user JWT in a background task:** the token can be close to expiry when it arrives. supabase-js refreshes it only about 90 s before `exp`, and the default lifetime is 1 h. A large file, slow embeddings or OpenAI retries can outlast it, and the task has no way to refresh it. The startup sweep also crosses users, so it can't run under any single user's JWT.
- **Choice:** `create_service_client()` is used **only** in `app/services/ingestion.py`, by `process_document` and the startup sweep. Never in a router.
  - Upload, list, get and delete all run as the user. The `documents` insert and Storage upload go through RLS and Storage policies, so the user's ownership of the document id is proven before the task starts.
  - The task receives only that `document_id`. Every service-role query filters by `id`/`document_id`, and `user_id` is copied explicitly from the document row.
- **Gotcha:** `default auth.uid()` is NULL under the service role. `chunks.user_id` is `not null`, so if the code forgets to set it the insert fails loudly instead of creating orphan rows.
- **Least privilege:** users get **no** insert/update policy on `chunks` and no update policy on `documents`. Only the backend (service role) can write embeddings or change status, so a user can't inject vectors or fake `completed` through the REST API.
- **Record it:** this is a deliberate exception to 1.1's "no service-role key in request paths". It still holds, since request paths stay user-scoped. Note it in `.claude/memory/ingestion.md`.

### 3. The backend receives the upload (multipart) and writes to Storage with the user's JWT
- One request does validation (type, size, UTF-8, no NUL bytes) on the server and can be tested with curl.
- The browser never needs Storage write logic.
- Rejected alternative: the browser uploads straight to Storage and then calls a "register" endpoint. That means two calls, orphan handling and duplicated validation.

### 4. Chunker: character-based recursive splitter, **1500 chars, 200 overlap**, no new dependency
- 1500 chars is about 350 to 400 tokens of English. That's far under the 8191-token input limit of `text-embedding-3-small`, small enough for precise retrieval, and cheap to put into chat context in 2.3. 200 chars (about 13%) of overlap keeps a sentence that straddles a boundary retrievable from both sides.
- Token-based splitting would add `tiktoken` (tied to one model family) and gains little at these sizes. Characters are a good enough proxy and match the env-var names.
- Separators in priority order: `"\n\n"`, `"\n"`, `". "`, `" "`, then a hard cut. Markdown headings start after blank lines, so `"\n\n"` keeps sections together.
- The interface `chunk_text(text, size, overlap) -> list[str]` is kept small so Module 5 (docling) can swap it.
- Configurable with `CHUNK_SIZE` and `CHUNK_OVERLAP`.

### 5. Realtime
- `documents` joins the `supabase_realtime` publication. The frontend subscribes to `postgres_changes` on `public.documents` with filter `user_id=eq.<uid>`.
- RLS is enforced for each subscriber, and the filter cuts noise.
- DELETE events can't be RLS-checked or filtered, so their payload carries only the primary key. The UI removes a row as soon as `DELETE /api/documents/{id}` succeeds, and only uses Realtime DELETE events to drop ids it already has.
- Keep the default replica identity (don't set `FULL`).

## Shared contract (2.3 depends on this, don't rename anything)
- Migration `supabase/migrations/0003_documents_chunks.sql`. The `vector` extension is installed in schema `extensions`, so the column type is `extensions.vector(1536)` and the index uses `extensions.vector_cosine_ops`. 2.3 should use the `<=>` operator and `set search_path = public, extensions` in `match_chunks`.
- `public.documents(id, user_id, filename, storage_path, mime_type, size_bytes, status ∈ pending|processing|completed|failed, error, chunk_count, created_at, updated_at)`, in the `supabase_realtime` publication.
- `public.chunks(id, document_id → documents on delete cascade, user_id, chunk_index, content, embedding vector(1536), created_at)`, with an HNSW cosine index and `unique (document_id, chunk_index)`.
- **Only `completed` documents have chunks.** A failed run deletes its partial chunks.
- `app/services/embeddings.py` exports `embed_texts(texts: list[str]) -> list[list[float]]` and `embed_query(text: str) -> list[float]`. **Both are sync.** 2.3 must use `embed_query` so query and document vectors share the model and dimensions. It calls `embed_query` from a worker thread.
- Storage bucket `documents` (private), object key `{user_id}/{document_id}/{safe_filename}`.

### 3. Chunker `backend/app/services/chunking.py`
- `chunk_text(text: str, size: int, overlap: int) -> list[str]`:
  - Normalize `\r\n` to `\n`, strip. Empty text gives `[]`.
  - Split recursively on separators (`\n\n`, `\n`, `. `, ` `), keeping each separator attached to its piece so no text is lost. A piece longer than `size` is re-split with the next separator, with a hard cut at `size` as the last resort.
  - Merge pieces greedily into chunks of at most `size` chars. When a chunk is emitted, seed the next one with the previous chunk's trailing pieces, up to `overlap` chars in total.
  - Strip each chunk and drop empty ones.
  - Assert `0 <= overlap < size`.
- `backend/app/scripts/check_chunker.py`: plain asserts, no pytest (2.3 introduces pytest later; these can move into `backend/tests/` then). Cases:
  - Empty and whitespace input give `[]`.
  - 100 chars give exactly 1 chunk.
  - Every chunk is at most `size` on the sample `.md` and on generated prose.
  - Consecutive chunks of prose share overlapping text.
  - 10,000 chars with no whitespace give `ceil(10000/1500)` hard-cut chunks.
  - Every sentence of the input appears in some chunk.
  - Output is deterministic.
  - Print the chunk count and lengths for `test-data/ingestion/velmora-station.md`.
- *Validate:* `cd backend && venv/bin/python -m app.scripts.check_chunker` prints `OK` and the sample's chunk lengths (expect 2 to 3 chunks, all at most 1500).

### 5. Ingestion pipeline `backend/app/services/ingestion.py`
- Constants and helpers:
  - `BUCKET = "documents"`
  - `SUPPORTED_TYPES = {".txt": "text/plain", ".md": "text/markdown", ".markdown": "text/markdown"}`. M5 extends this map.
  - `class UnsupportedFile(ValueError)`
  - `decode_text(data: bytes) -> str`: `data.decode("utf-8-sig")`. Raise `UnsupportedFile` on `UnicodeDecodeError` or if the text contains `\x00`, because Postgres `text` rejects NUL.
  - `safe_filename(name)`: keep `[A-Za-z0-9._-]`, replace everything else with `_`, cap at 100 chars, fall back to `file`.
  - `storage_path(user_id, doc_id, filename)`.
- `@traceable(name="ingest_document", run_type="chain") def process_document(document_id: str) -> None`. It's sync and runs in the threadpool. Uses `create_service_client()`.
  1. Load the row by id; return if it's gone (deleted meanwhile).
  2. `_dev_delay()`, then update to `status='processing'` and `updated_at=now`.
  3. `download(storage_path)` → `decode_text` → `chunk_text(CHUNK_SIZE, CHUNK_OVERLAP)`. If the result is empty, raise "No text content found".
  4. Delete existing chunks for the document so a re-run is idempotent and ready for M3. Then, per batch of 100: `embed_texts`, then insert rows `{document_id, user_id: doc["user_id"], chunk_index, content, embedding: list[float]}`. PostgREST turns a JSON array into a `vector`.
  5. `_dev_delay()`, then update `status='completed'`, `chunk_count`, `error=None`, `updated_at`.
  6. On any exception: `logger.exception`, best-effort delete of partial chunks, then update `status='failed'`, `error=str(exc)[:1000]`, `updated_at`. That update is wrapped in its own try, so a deleted row or other failure only gets logged.
  - Pass LangSmith metadata `{document_id, user_id, chunk_count}`.
- `fail_interrupted_documents()`: one service-role update of all `pending`/`processing` rows to `failed` with the restart message. If the service key is missing, it logs and skips.
- `ingestion_configured() -> str | None` returns the reason ingestion can't run (no service key / no OpenAI key), or None.
- *Validate:* `venv/bin/python -c "from app.services import ingestion; print(ingestion.decode_text(b'\xef\xbb\xbfhi'))"` prints `hi`, and `decode_text(b'\xff\xfe\x00')` raises `UnsupportedFile`. The full pipeline is validated in Task 6.

```markdown
# Velmora Research Station: Field Handbook

## Overview
Velmora Research Station sits on the eastern shore of Lake Velmora at an elevation of 2,340 metres. It was founded in 2009 by the Northern Limnology Consortium to study cold-water algae blooms. The station runs year-round with a winter crew of seven and a summer crew of up to twenty-two researchers.

The station's call sign on the regional radio net is "Heron Two". The backup call sign, used only when the main antenna is down, is "Grey Reed".

## Arrival and access
Visitors arrive by the gravel service road from Port Analen, a drive of roughly three hours. From November to April the road is closed beyond the Kestrel Pass gate, and the only access is the station's tracked snow vehicle, nicknamed "Old Margit". Every visitor must check in with the duty officer within thirty minutes of arrival and sign the red logbook kept beside the boot room.

## Daily schedule
Breakfast is served at 06:45 and the morning briefing starts at 07:30 in the map room. Lake sampling runs from 08:00 to 12:30. The sampling boat, the "Tern", may not leave the dock if wind speed at the north buoy exceeds 9 metres per second. Afternoons are for lab work and data entry. Dinner is at 18:30, and quiet hours begin at 22:00.

## Sampling protocol
Water samples are taken at three fixed depths: 0.5 metres, 4 metres and 12 metres. Each bottle is labelled with the site code, the depth and the time in UTC. Samples must reach the cold room within 40 minutes of collection, and the cold room is held at 4 degrees Celsius. Chlorophyll readings are logged in the shared spreadsheet called LAKEBOOK, never on paper.

## Safety
Life jackets are mandatory on the dock and on the boat at all times. The emergency muster point is the flagpole in front of the generator shed. In case of fire, the alarm is three long blasts on the air horn. The nearest hospital is in Port Analen, and the station keeps a satellite phone in the duty office; its battery is checked every Monday.

## Power and supplies
Electricity comes from a 48-panel solar array and a diesel generator that starts automatically when the battery bank drops below 35 percent. Fresh food is delivered every second Thursday. Coffee is rationed to four cups per person per day in winter, a rule the crew calls "the Margit limit".

## Data and computing
All raw instrument data is copied nightly at 02:00 to the station server, named "loon". The server keeps 90 days of history; older data is archived to the consortium's cloud bucket every Sunday. Researchers must not install software on the lab workstations without approval from the IT lead, Dr. Ilse Varga.

## Wildlife
Lake Velmora is home to a breeding colony of black-throated divers. Between May and July the northern bay is closed to boats to protect nesting sites. Brown bears are occasionally seen near the waste store, so food scraps go in the locked bear bin, never in open bags.
```
